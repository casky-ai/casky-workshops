07 / 13 · THE LOOPLINE STORY
WHAT VIBE CODING DID, AND DIDN'T FIX

Same story. This time,
we're the ones who broke it.

Lovable scaffolded Loopline's database. It never turned Row-Level Security on for the customers table. Not disabled by a developer, never enabled at all.

Weeks later, a security blog post scared the founder into fixing one table. tickets got a policy, but it was USING (true), which matches every row for every requester. Looks fixed in a schema diff. Isn't. customers was never revisited.

Meanwhile, an env var named NEXT_PUBLIC_SUPABASE_SERVICE_ROLE_KEY shipped Supabase's admin key straight into the browser bundle, because the coding assistant didn't flag what NEXT_PUBLIC_ does in Next.js. Nobody caught it before it shipped.

Two checks. Five minutes. Let's run them.

08 / 13 · LIVE CHECK 1 OF 2
THE FIVE-MINUTE CHECK

rowsecurity: false.
That's the whole bug.

 check_1_rls.sh
# Does the public anon key read tables it shouldn't?
$ curl -s "loopline.../rest/v1/customers?select=*" \
  -H "apikey: <key shipped in the JS bundle>"
→ every customer row, no login required.
rowsecurity: false
The apikey is the public "anon" key. It's meant to ship to every browser, that's how Supabase apps normally talk to the database from the client.
rowsecurity: false is Postgres's own flag: Row-Level Security was never turned on for this table. No policy exists to check who's asking.
The result: the same public key every visitor already has is, by itself, enough to read every row. No password, no session, no exploit.

09 / 13 · LIVE CHECK 2 OF 2
THE FIVE-MINUTE CHECK

The admin key. In the browser.
On purpose, sort of.

 check_2_secrets.sh
# Is a secret sitting in plain sight in the shipped bundle?
$ curl -s loopline.io/_next/static/chunks/*.js \
  | grep -oiE '(service_role|sk-live-|AKIA)[A-Za-z0-9_.":-]{5,}'
→ NEXT_PUBLIC_SUPABASE_SERVICE_ROLE_KEY, in the client bundle.
Supabase's admin key. Bypasses RLS entirely, by design.
The anon key (check 1) respects Row-Level Security, when RLS is configured correctly, it's the safe key to expose.
The service_role key is Supabase's admin key. By design it bypasses RLS entirely, correctly configured or not. It's meant only for trusted, server-side code.
How it got here: an env var named NEXT_PUBLIC_SUPABASE_SERVICE_ROLE_KEY. The NEXT_PUBLIC_ prefix ships anything to the browser, by Next.js design, not a bug in Next.js.
